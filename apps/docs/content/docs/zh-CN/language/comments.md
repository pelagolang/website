**决定（所有者，2026-10-20）：** 选项 B，文档注释使用 `//~`。`/// text` 是普通行注释，`///* ... *///` 是普通块注释（可嵌套），`//~ text` 是文档行，`//~* ... *~//` 是文档块（不可嵌套）。`//` 和 `/* */` 是带提示的词法错误；`////` 只是普通注释（它以 `///` 开头）。文档附着于其后的条目；没有单独的文件级形式（后面什么都没有的文档注释不属于任何东西）。本页其余部分是得出这一决定之前的讨论；其中选项 B 提到的 `//!` 写法已变为 `//~`。


## 现状 [#where-we-are]

目前（`lexer.rs`、`keywords.md`、`lexer.md`）：`// line`、`/* block */`（可嵌套）、`/// doc line`、`///* doc block *///`，以及作为普通注释的 `//// ...`（因此一排斜杠组成的横幅不算文档）。所有者的看法：`//` 和 `/* */` 在 C、Java、Rust 和 Go 中已经存在，所以并不是我们自己的；`///` 应当是普通行注释，`///* ... *///` 应当是多行注释。去掉 `////`。

## 注释语法需要涵盖什么 [#what-a-comment-syntax-has-to-cover]

1. 给读者的一句备注，直到行尾。
2. 跨多行的备注，或位于行中间的备注（`f(1, /* why */ 2)`）。
3. 被注释掉的代码（一个区域，可以快速开关）。
4. 对其后条目的文档（在悬停提示中显示，供工具使用）。
5. 对文件或模块本身的文档（文件头；其后没有条目）。
6. 给工具用的标记（`TODO`、格式化器关/开、脚本用的首行 `#!`）。

任何选择都要经过两个实用测试：

- **切换测试。** 编辑器通过添加一个固定的行前缀来注释选区，再通过移除它来取消注释。这个前缀不能是另一种注释形式的开头，否则切换文档行会剥掉一半（`/// doc` 丢掉 `//` 变成 `/ doc`）。这就是 VS Code 扩展目前存在的缺陷。
- **成本测试。** 每种形式都是一条词法规则、一条语法规则（TextMate、tree-sitter）、一项编辑器配置，以及格式化器中的一行。形式越少，需要保持同步的东西越少。

## 选项 [#options]

**A. 所有者的写法，两种形式。** `/// text` 是普通注释，直到行尾。`///* ... *///` 是多行注释，同时也是文档注释（一行或多行）。没有 `//`，没有 `/* */`，没有 `////`。
- 涵盖 1（行）、2（块）、3（多行 `///`，切换干净）、4 和 5（条目前或文件顶部的 `///*` 块）。
- 除非用块来实现，否则没有单独的文档行，也没有行内中间注释；而这样一来块注释就是文档注释：`f(1, ///* why */// 2)` 会被算作不属于任何东西的文档。
- 切换测试：行前缀 `///` 是 `///*` 的开头，所以切换文档块中的某一行有同样的剥掉一半的问题，不过文档块很少需要切换。

**B. 所有者的写法，四种形式，彼此分开。** `/// text` 普通行；`///* ... *///` 普通块（可嵌套）；`//! text` 文档行；`//!* ... *!//` 文档块。文档形式绝不以普通行前缀开头，所以能通过切换测试。单独的 `//` 不是注释（会报错，提示“请使用 `///`”）。
- 涵盖 1 到 6（文件顶部的 `//!` 为文件写文档）。
- 四种形式；比 C 系语言多一条要学的规则，但每一种都是前一种的简单变体。

**C. 另一个家族，使用 `#`。** `# text` 普通行，`#* ... *#` 块，`## text` 文档行，`#** ... **#` 文档块。目前 `#` 在字符串之外是空闲的（它只在字符串内部表示插值）。
- 简短，脚本语言里很常见，并且与 C 毫无共同之处。
- 首行 `#!` 很自然地适配。代价：`##` 以 `#` 开头，所以文档行通不过切换测试；字符串中的插值 `#name` 读起来与注释 `#` 不同。

## 建议 [#recommendation]

**B。** 它把你的 `///` 和 `///*` 原样保留为普通形式，从设计上解决了切换问题，把文档与备注分开（因此被注释掉的区域绝不会是文档），并涵盖列表中的所有情形。A 最小，但它让文档与块注释成为同一回事，行内情形就没有位置了。

## 问题 [#questions]

1. A、B 还是 C？
2. `///* ... *///` 是否嵌套（注释掉一个已经包含块的区域）？建议：是，与目前的 `/* */` 一样。
3. 单独的 `//` 是错误（并提示写成 `///`）还是被忽略？建议：错误。否则出于习惯留下的 `//` 会悄悄变成代码。
4. 文档块：在 B 中，`//!* ... *!//` 是文档块。这个写法可以接受，还是更喜欢别的（`///**`）？
5. 文档注释是否只附着于其后的条目，并用 `//!` 表示外层模块或文件？建议：是。
6. 像 `/////////////` 这样的横幅是否允许作为普通注释？在 B 中本来就可以（一条 `///` 行）；不需要额外规则。
7. 我们是继续识别 `//` 和 `/* */` 一个版本并提供 `pelago fmt` 改写，还是立刻切换？建议：立刻切换；目前还没有用户，只有我们自己的示例。
