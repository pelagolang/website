Два вопроса о памяти, которые предыдущие страницы оставили открытыми: массив структур против структуры массивов
и линейные типы.

## 1. Где мы сейчас [#1-where-we-are]

Значения имеют владельца. Параметр `sink` или `move` забирает значение, `deinit` выполняется, когда значение
выходит из области видимости, а перемещённое значение нельзя использовать снова. На языке теории типов это
**аффинность**: значение можно использовать не более одного раза, и его также можно отбросить.

## 2. AoS и SoA [#2-aos-and-soa]

- **AoS** (array of structs, массив структур): поля каждого элемента лежат вместе. Так C размещает `point[]`, и
  это то, чем в этом языке является `[point]`. Это правильное размещение, когда вы работаете с элементами целиком,
  и оно совпадает с C для взаимодействия.
- **SoA** (struct of arrays, структура массивов): по одному массиву на каждое поле. Это правильное размещение,
  когда цикл трогает одно поле (все значения `x`): данные плотно лежат в кэше и хорошо векторизуются.

**Предложение.** По умолчанию используется AoS, потому что он предсказуем и совместим с C. SoA включается явно,
как тип коллекции с тем же интерфейсом:

```
var points: soa<point> = soa []
points.push!(point { x: 1.0, y: 2.0 })

points[0].x                  // reads through a view of element 0, same code as a list
points.x                     // the whole x column as a read-only [float]: a SIMD-friendly slice
for inout p of points { p.x += 1.0 }
```

Поскольку при семантике значений ссылки временные (второго класса), `points[i]` всегда является представлением,
которое существует в течение одного оператора, поэтому размещение за ним можно менять, не меняя код, который им
пользуется. Это реальное преимущество перед языками, где ссылки на элементы могут «убежать». `soa<point, 8>` —
блочный вариант (AoSoA), который группирует по 8 элементов в блок под ширину векторов.

Компилятор, который сам выбирает размещение, остаётся в списке «на потом». Для него нужен анализ всей программы.

Кортеж фиксированного размера `(A, B; N)` — это чередующееся размещение, AoS-вариант для смешанных типов.
`soa<T>` — его противоположность, так что вместе они покрывают оба конца.

## 3. Линейные типы [#3-linear-types]

Аффинные типы позволяют молча отбросить значение. **Линейные** типы это запрещают: значение должно быть
использовано ровно один раз. Так «этот файл должен быть закрыт», «эта транзакция должна быть зафиксирована или
отменена» или «это разрешение должно быть возвращено» превращаются в ошибки компиляции. В Rust линейных типов
нет (только предупреждения). В Austral и Hylo они есть.

**Предложение.** Мы почти уже там. Добавим необязательный модификатор:

```
linear struct transaction { ... }

fn commit(sink t: transaction) -> void ! db_error { ... }
fn rollback(sink t: transaction) { ... }

fn work() -> void ! db_error {
    const t = begin()?
    do_things(t)               // read-only use, fine
    t.commit!!()               // consumed. Forgetting this is a compile error.
}
```

- Линейное значение должно быть использовано на каждом пути, включая ранние возвраты и `?`. Компилятор сообщает,
  какой путь его забыл.
- У линейного типа нет `deinit`, потому что его никогда нельзя отбросить неявно.
- `sink` уже означает «забирает значение», а `!!` уже отмечает потребляющий вызов, поэтому нового синтаксиса в
  месте вызова не нужно.
- С обобщённым кодом нужна осторожность: по умолчанию параметры типов можно отбрасывать, поэтому `T` не может
  быть линейным типом, если ограничение этого не говорит (`<T: linear>`). Держите эту дверь открытой при
  проектировании проверки типов; нигде не зашивайте «любой тип можно отбросить».

**Этапы.** Версия 1 — аффинность плюс предупреждение `@must_use`. Настоящие типы `linear` появятся после
проверки типов, потому что они меняют правила для обобщений. Слово `linear` зарезервировано уже сейчас (мягкое
ключевое слово).

## Реализовано: soa [#built-soa]

`soa<T>` для структуры `T` работает так, как описано выше (см. IR24 в `ir.md`): `soa []`, `soa [a, b]`, `push!`, `pop!`, `insert!`, `remove!`, `clear!`, `len`, `points[i]`, `points[i].x`, `points.x`, циклы `for` и `for inout`, `copy`, `==`, `print`. Блочная форма `soa<T, N>` принимается и ведёт себя так же; её блочное размещение в памяти оставлено бэкенду.

## Временные значения [#temporaries]

Значение, которое создано, но никогда не получало имени (результат функции, который вы игнорируете, объект за `make_dog("a").name`, аргумент, построенный на месте), уничтожается в **конце своего оператора** в порядке, обратном созданию. Если его забирает что-то (переменная, поле, параметр `sink`, `return`), то позже его уничтожает новый владелец. Компилятор ведёт этот учёт при построении кода (книга учёта, IR22); в линейном коде нет накладных расходов во время выполнения сверх того, что уже платят переменные.

## Решения черновика 1 [#decisions-from-draft-1]

- **M1** AoS — размещение по умолчанию. `soa<T>` — необязательная коллекция, `soa<T, 8>` — её блочный вариант.
- **M2** Доступ к столбцу (`points.x`, `[float]` только для чтения) входит.
- **M3** Размещение, выбираемое компилятором, остаётся оптимизацией на потом.
- **M4** `linear` — необязательный модификатор, запланированный после проверки типов. Слово зарезервировано уже сейчас как мягкое ключевое слово.
